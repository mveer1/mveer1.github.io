# Developing the site

How to run, extend and check the world. The short overview is in the [README](../README.md); the module map and the rules that keep it maintainable are in [architecture.md](../architecture.md). Design rationale lives in the other documents in this folder.

## Run it

There is no build step; GitHub Pages serves the repository as is.

```bash
npm install          # dev tools only (Vite, Playwright, http-server)
npm run dev          # Vite dev server, then open the printed URL
npm run serve        # or a plain static server, exactly how GitHub Pages serves it
```

URL options: `?q=low|medium|high` locks a quality tier; `?islands=works,lab` builds only some islands (the Harbour is always built); `#visit-gl-recon` opens an exhibit on load; `#guide` opens the field guide.

Vanilla Three.js 0.170 is loaded as ES modules through an import map in `index.html` and `lab.html` (no bundler, zero-build deploy). `three@0.170.0` is also a dev dependency, only so the Vite dev server can resolve the bare `three` import; the deployed page loads it from the CDN, so keep the two versions in step. Bumping Three.js means changing the version in both import maps and in the `modulepreload` URLs of `index.html`, not just in `package.json`.

## Generated parts of index.html

Two blocks of `index.html` are written by scripts. Do not edit them by hand.

| Block | Command | Run it after |
|---|---|---|
| Field guide (all portfolio content as plain HTML) | `npm run guide` | editing `js/content/content.js` |
| `modulepreload` hints for the module graph | `npm run preload` | adding, moving or removing a statically imported module |

## Add a portfolio project

1. Add an entry to `EXHIBITS` in `js/content/content.js` with `id`, `island`, `object` (what it is in the world), `title`, `kicker`, `line`, and any of `metrics`, `paragraphs`, `steps`, `stack`, `links`. Use only facts from a source you can name; record the source in `docs/portfolio-content-inventory.md`.
2. In the island's module (`js/world/islands/<island>.js`), build the object and push an exhibit:
   ```js
   ctx.exhibits.push({ id: 'my-project', marker: [x, y, z], stand: [x, z], face: [x, z], hit: [x, y, z, w, h, d], shot: { side: 35 } });
   ```
   `stand` is where the figure stands, `face` what it looks at, `hit` the clickable box (local studs). The camera is auto-framed; `shot.side`, `dist`, `el` nudge it.
3. Add a beat to `ctx.beats` where it belongs on the walk: `{ id: 'my-project', len: 1, exhibit: 'my-project', char: [[x, z]] }`.
4. Run `npm run guide` to refresh the static field guide, then `node qa/tour.mjs --only <island> --panels` and look at the shots.

## Add an island

1. Create `js/world/islands/<id>.js` exporting `build(ctx)`. Use `buildTerrain` for the ground, the props in `props.js`, set `ctx.occ = b.occ; ctx.camOcc = b.camOcc;` after `b.build()`, and fill `ctx.exhibits`, `ctx.beats`, `ctx.ports`, `ctx.spawn`.
2. Register it in `LAYOUT` (origin) and `BUILD_ORDER` in `js/world/world.js`, add it to `ROUTE` if the tour visits it, and add a bridge to `BRIDGES`.
3. Add it to `ISLANDS` in `content.js` and give it a colour in `ui/map.js`.
4. Run `npm run preload`, then `npm run qa:reach` to prove the new island is reachable.

## Asset workflow

There are no model files. Every brick is generated by `js/lego/parts.js` from a few numbers (stud pitch 1, plate 0.4, brick 1.2; chamfered edges; seams; studs only where nothing covers them) and merged by `BrickBuilder` into one mesh per material class per island. To add a part type, add a function to `DEF` in `parts.js`, look at it in `lab.html` (`node qa/shoot.mjs --url lab.html --out qa/shots/lab.png`), then use it with `b.put(type, args, x, y, z, colour)`. Why procedural instead of Blender is explained in `technical-tooling-audit.md`.

Besides the favicon, the only image in the repository that the page refers to is `assets/images/social-preview.png` (the link-preview card); everything else on screen is generated. The CV, `mahavir.pdf`, is the canonical source for every metric shown; see `portfolio-content-inventory.md` for the precedence rules.

## Performance

- The hero is plain HTML on a CSS sky, so it paints before any 3D code arrives: fonts are self-hosted (`assets/fonts/`, latin subset, preloaded), three.js is the minified build, and every module the world needs is `modulepreload`ed in parallel. The canvas fades in over the sky when the first frame is ready; the page is scrollable from first paint, and a hero button pressed early is replayed once the world is up.
- Hero scroll motion: the title lines roll up with the page via CSS scroll-driven animations (compositor thread; `--hero-p` from an inline script in browsers without them), and the first chapter card rolls up from below. The title beat's camera drifts toward the first stop (`HERO_DRIFT` in `js/camera/journey.js`) so scrolling the hero visibly moves the world.
- Zero model downloads; islands are generated in 10 to 81 ms each, one at a time after the Harbour is on screen.
- About 3 to 5 draw calls per island (merged plastic, transparent, glow and metal meshes) plus small animated parts.
- Three tiers (`core/quality.js`): pixel ratio, shadows, bloom, tilt-shift, MSAA, stud detail and light-pool size. The starting tier comes from device hints; a governor drops a tier when p75 frame time passes 26 ms.
- Shadows follow the active island and refresh only occasionally on very wide shots.
- Measured on Apple M2 in Chrome: p50 and p90 frame time 16.7 ms on every tier; about 0.9 to 1.0M triangles on the widest shot at high, 0.27M at low.

## Camera and walkability

- Authored shot distances are multiplied by `PULLBACK` (2.0) in `js/world/world.js`, so the tour and the exhibit panels show a whole building and the paths around it. Overview shots (60 studs and more) are left alone. The free-walk camera starts 40 studs back and zooms from 12 to 76 (wheel, `+` / `-`); when a building is in the way it rises first and only steps in as a last resort, never closer than 60% of the zoom. The free camera (C) zooms out to 170.
- Bridges land on solid deck: `WalkMap.landing()` moves a bridge end onto the nearest standable cell, so the figure can always step on and off.
- `node qa/reach.mjs` checks the walk map the way the controller walks it (blocked cells, gaps, one-brick steps), then rides every cable car, lift and zip line. Anything unreachable fails the run.

## Accessibility

Field guide (static HTML, works without JavaScript or WebGL) and a skip link to it; every action on the keyboard (`game-design.md`, Controls); dialogs with focus handling; reduced motion replaces camera moves with cuts and stops stepped loops; UI text meets WCAG AA (ink 14:1, muted 6.2:1, accent 5.4:1 on paper).

## Checks

```bash
npm run check                        # node --check on every file in js/, tools/ and qa/
npm run qa                           # behaviour checks: tour, walking, jump, falling off edges, camera, free camera, autoplay and speed, Escape, arcade
npm run qa:reach                     # flood-fill: every island, exhibit, beacon and ride is reachable
npm run qa:tour                      # screenshot every beat and panel into qa/shots/tour
npm run qa:storyboard                # regenerate docs/camera-storyboard.md
node qa/shoot.mjs --url / --mobile --w 390 --h 844 --out qa/shots/m.png
```

`qa/shots/` is git-ignored output. The browser scripts launch an installed Google Chrome (`channel: 'chrome'`) with the Metal GPU backend, not Playwright's bundled browser, so they are written for macOS with Chrome installed.

## Known limitations

- Not tested on real phones; mobile was checked in emulation only.
- A few exhibit frames still have a lamppost at the edge.
- The tour is long (about 45 screens); the map, stop arrows and chapter list shortcut it.
- The 3D scene is not navigable by screen readers; the field guide is the equivalent.
- See `visual-review.md` for scores and the full list.
